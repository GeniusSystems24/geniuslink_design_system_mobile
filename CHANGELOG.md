## 1.0.3 - 2026-09-25

### Changed

- Adopted `SuperGrid` from `super_core` as the responsive layout foundation across feature screens.
- Migrated inventory page-view screens under `lib/features/inventory/presentation/widgets/page_views` to responsive grid layouts where appropriate.
- Migrated feature page views under `lib/features/**/presentation/widgets/page_views` to use `SuperGrid`.
- Migrated screens under `lib/features/**/presentation/widgets/*_views.dart` to use responsive grid layouts.
- Migrated account screens under `lib/features/accounts/presentation/pages/*_screen.dart` to use `SuperGrid`.
- Migrated views under `lib/features/more/presentation/widgets/*_view.dart` to use `SuperGrid`.
- Migrated views under `lib/features/reports/presentation/widgets/*_view.dart` to use `SuperGrid`.
- Migrated views under `lib/features/settings/presentation/widgets/*_view.dart` to use `SuperGrid`.
- Migrated views under `lib/features/admin/presentation/widgets/*_view.dart` to use `SuperGrid`.
- Added responsive field layouts using mobile, tablet, desktop, and large breakpoint column spans.
- Added responsive detail layouts for key/value and information sections.
- Kept semantic structures such as transaction rows, history lists, journal lines, trees, queues, and other order-sensitive content full-width where reflow would change meaning.
- Preserved scroll behavior and bounded-height requirements for screens that depend on constrained layouts.

### Fixed

- Fixed malformed `SuperGrid` code generated by an earlier migration script where `child:` was incorrectly repeated before `scope`, `children`, `SuperGridCell`, and nested widget lines.
- Fixed invalid grid structures that caused missing `children`, undefined `child`, undefined `scope`, and syntax errors.
- Added repair logic for already-damaged `SuperGrid` blocks without requiring restoration from an older project copy.
- Improved migration scripts to avoid using semantic prefixes such as `child:` as indentation.
- Added structural validation to detect malformed `SuperGrid` blocks before completing migrations.

### Tooling

- Added idempotent migration scripts so repeated execution does not duplicate layout changes.
- Added timestamped migration backups before modifying project files.
- Added `--dry-run` support for previewing planned changes.
- Added optional Dart formatting and Flutter analysis after migrations.
- Added screen-aware migration logic that preserves existing controllers, callbacks, validation, data sources, and business logic.

## 1.0.1 - 2026-09-24

### Changed

- Upgraded `super_table_field` from `3.1.1` to `3.2.0`.
- Ensured the direct `super_auto_suggestion_box` dependency is compatible with
  `super_table_field 3.2.0` (`>=1.6.0 <2.0.0`).
- Updated custom suggestion-builder callbacks to receive `BuildContext` as the
  first parameter where required by the new autocomplete integration.
- Kept existing `SuperComboColumn.advancedSearch` and
  `SuperComboColumn.leading` behavior unchanged.
- Updated project documentation for the `1.0.1` dependency baseline.

## 3.2.1 - 2026-09-24

### Changed
- Upgraded `super_form_field` from `^1.14.0` to `^1.15.0`.
- Migrated `SuperSelectFormField` from deprecated `sources` / `SuperSelectListSource` usage to the `source` / `SuperSelectSources.list(...)` API.
- Exported the new `SuperSelectSources` and `SuperMultiSelectSources` factories from the shared form adapter and removed deprecated select-source exports.
- Upgraded `super_auto_suggestion_box` to `^1.7.0`.
- Migrated suggestion builders to the BuildContext-aware `(context, items, index, item)` signature required since `1.6.0`.
- Adopted the `1.7.0` remote-loading contract: context-aware remote callbacks, immediate local matching, remote-only debounce, and optional `minResult` behavior.
- Updated `README.md` with the v3.2.1 package baseline and migration rules.

### Validation
- Preserved `SuperChoiceFormField.options`; it is not part of the `super_form_field 1.15.0` source migration.
- No project usages of auto-suggestion `async`, `hybrid`, `remoteFallback`, `paged`, or direct `query` / `progressive` / `fetchPage` APIs were present at migration time, so no speculative remote-fetch thresholds were introduced.
